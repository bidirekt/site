── two contracts, one comparison

The provider declares what it produces. The consumer declares what it reads. Neither knows about the other; both publish to the broker.

The broker checks that every required property on the reading side exists, with the same type, on the producing side. Two lines below don't line up — and that is the whole report.

── provider · petstore_apicontract.yaml
provides:
  rest:
    "/pets/*":
      get:
        responses:
          "200": Pet
schemas:
  Pet:
    type: object
    properties:
      petId: { type: integer }
      name: { type: string }
      weight: { type: integer }
      photoUrl: { type: string }
produces · extra fields are free
── consumer · petstore_webcontract.yaml
consumes:
  petstore_api:
    rest:
      "/pets/*":
        get:
          responses:
            "200": Pet
schemas:
  Pet:
    type: object
    properties:
      petId: { type: integer }
      name: { type: string }
      weight: { type: string }
      status: { type: string }  # missing in provider
reads · every required property is a check · 2.3.0

── 1 · publish

Each participant declares what it provides and what it consumes in one YAML file, and publishes it under a version.

$bidirekt publish ./contracts/*.yaml
--participant petstore_api --version 1.5.0
petstore_api contract publish successful
── 2 · can-i-deploy

Ask before you deploy. The broker compares the new version against what is deployed; the exit code is the gate in CI.

$bidirekt can-i-deploy petstore_api
--version 1.5.0 --environment production
petstore_api can be deployed to production
── 3 · record-deployment

After the deploy succeeds, tell the broker which version now runs where. That is the state the next check compares against.

$bidirekt record-deployment petstore_api
--version 1.5.0 --environment production
petstore_api deployment recorded to production
bidirekt version 0.1.0
